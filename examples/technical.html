One file. Two paths.

The API publishes your HTML. An isolated viewer delivers it. Private storage connects the two.

A link to read.
A key to change.

Keep publishing and reading separate.
The API accepts uploads and manages revisions. The viewer serves access-checked HTML under /rendered/, inside an opaque sandbox.
Store metadata apart from bytes.
PostgreSQL keeps document state, access rules, and revision references. Private file storage holds the HTML. Every update writes a new revision.
Check access before delivery.
A sharing link does not grant editing rights. Password-protected documents require a reader grant; changes require the document’s management key.

The publishing contract.

Accept one UTF-8 HTML file with inline scripts, styles, and embedded assets. Return a stable URL plus a private management key. Updates use an ETag to reject stale edits. 

POST /api/v1/documents
file: idea.html

→ url: the sharing link
→ manageKey: keep private
→ etag: use for the next change

Review the failure paths.

  • If file storage fails, do not publish a revision that points to missing bytes.
  • If two updates arrive together, reject the stale ETag rather than silently overwriting newer work.
  • If access changes, invalidate existing viewer grants before serving more content.
  • If a document is deleted, stop delivery immediately and purge stored bytes after retention.
